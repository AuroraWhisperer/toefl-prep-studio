## 架构判断与建议

继续沿用现有 FastAPI + 原生前端的本地单体。题库与答案分离、服务端评分、普通练习／ETS 模考／综合测验各自的业务流程，以及 JSON 归档与可重建内存索引，均与当前个人桌面使用场景相符；维持[现有架构决策](architecture-implementation-2026-09-27.md#决策结论)。本次没有发现必须更换框架或数据库的证据。

以下保留初次审查时的优化建议与测量依据；题目筛选和统一写入已在同日后续实施，见文末。评分前全库校验仍保留：

1. **先筛选题目，再复制返回结果。** [QuestionStore.questions_for](../backend/question_store.py)调用 `all_questions()` 时先深拷贝全部 2,115 题，筛选后又深拷贝结果；`score_submission()` 每次还调用全库 `validate_integrity()`。本机在已加载题库上使用 `cProfile` 各运行 20 次：阅读填词题型查询平均 85.3 ms，其中深拷贝累计占约 96%；全库校验平均 541.1 ms。分析器本身增加开销，这些数字用于定位热点，不代表正常 HTTP 请求延迟。优先在 `questions_for` 内从缓存只读筛选，最后仅复制返回题目；保留排序、完整材料、返回对象可独立修改的合同。全库校验是否移到加载阶段应另行验证失效与重载规则，不直接删除。
2. **统一文件写入机制，保留各业务模块的锁与生命周期。** [模考](../backend/mock_exam.py)和[综合测验](../backend/adaptive_test.py)的 `persist` 都执行临时文件替换及 Windows 短暂文件占用重试；[历史归档](../backend/history.py)仅替换一次。在下一次存储改动时，可以把同一 JSON 原子替换机制放进现有 `archive_io.py`，让调用方继续负责路径、锁和索引失效。收益是重试规则一致、减少漏改；代价是共享写入函数影响多条保存路径，需要覆盖文件占用、写入失败及重试不重复归档。没有必要合并三套考试状态机或增加通用存储框架。

此次按钮缺陷也说明共享答题界面的进入状态需要显式恢复。现有 `showTestSession` 已是该职责的入口，因此在这里修复即可；仅凭格式化后文件变长，不构成拆分 `app.js` 的理由。

## 后续优化实施（2026-09-28）

- `questions_for()` 从缓存只读筛选、按原规则排序，最后仅深拷贝选中题目。保留固定卷题量、日常阅读 2／3／2／3 的完整材料顺序和嵌套数据隔离。修改前保存的 22 种合法查询（全科、各科、12 个题型）与修改后完整 JSON 逐一相同。
- 新增 `archive_io.write_archive()`，供普通历史、模考、综合测验及概率重置标记共用 UTF-8 JSON 原子写入。仅对替换时的 `PermissionError` 最多尝试四次，间隔 20／40／60 ms；其他写入错误直接传播，失败保留旧文件。临时文件尽力清理，清理失败不覆盖原始异常或误报已成功的保存。目录、锁、索引失效与业务状态机继续由原模块负责；录音二进制写入未变。
- 保留 `score_submission()` 每次调用 `validate_integrity()`。当前题库为进程内惰性缓存，没有统一失效／重载入口，测试也会替换或修改缓存；直接缓存“已校验”状态会改变检测语义。将校验移到加载阶段仍须单独设计与验证。

同机、预加载题库、无 `cProfile`、每项各 20 次的平均耗时如下；这是函数级短测，不能视为 HTTP 延迟保证，也不能直接与上文分析器数据比较。
